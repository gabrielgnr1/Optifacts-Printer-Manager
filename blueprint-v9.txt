#===============================================================================

###	1.1. PURPOSE AND SCOPE

# 	The script's core objective is to determine the correct destination for a
# 	given file (`.ps` or `.pdf`) by querying a database, matching the result
# 	against a local configuration file, and then executing the appropriate
# 	action—either moving the file to a directory or sending it to a system printer.
#   This script is a command-line utility with multiple operational modes.

###	1.2. WORKFLOW INTEGRATION AND CONTEXT

# 	This script is to coexists with the standard Optifacts printing system.
#	It is critical to understand that this special workflow is only triggered for jobs
#	destined for PDF output and does not alter existing non-PDF printing processes.
#	
#	- Standard Workflow Unaffected: All existing PHYSICAL printer definitions and rules
#	  in Optifacts (e.g., in menus 3-5, and 3-11-14-2 rules like "PRINTERPCX" or
#	  "PRINTERLAX") will continue to function normally without any impact from this script.
#
#   - Special PDF Workflow Trigger: This new workflow is triggered ONLY when an Optifacts
#	  job destination evaluates to a PDF output queue AND the variable `PS2PDF=` parameter of
#	  the `/u/optifacts/printer.dbs/PS_Printers.cfg` file is modified to point to the 
#	  `intercept_ps2pdf.pl` script.
#	  (Optifacts will follow the standard behavior if `PS2PDF=` is kept as `/usr/bin/ps2pdf`)
#
#	- The full execution chain is as follows:
#		1. A print job is initiated through an Optifacts printer queue configured for PDF output.
#		2. The printing system executes the primary program for that queue: `/u/optifacts/bin/pr_LayHtm`.
#		3. The `pr_LayHtm` program generates a temporary PostScript file.
#		4. `pr_LayHtm` calls `intercept_ps2pdf.pl`, which handles file naming, PDF
#		   conversion, and multi-destination copying.
#		5. `intercept_ps2pdf.pl` then calls THIS SCRIPT (`printer_manager.pl`) as an
#		   external program, passing the full path to a newly created file as a
#		   single command-line argument. This script then takes over to perform the final routing.

#===============================================================================
#             SECTION 6: VERBOSE PROGRAM WORKFLOW & ERROR HANDLING
#===============================================================================

#	-------------------------------------------------------------------------------
# 	PHASE 0. INITIAL STARTUP AND STRUCTURE VERIFICATION 

#	0.1. The script will first check if the configured `$working_directory` exists.
	# 	- If it does NOT exist, it will attempt to create it with `$default_permission`.
	#	- If creation FAILS, it will set an internal "fallback mode" flag. All derived 
	#	  paths will be automatically re-pointed to a temporary directory
	#	  (e.g., `/tmp/printer_manager_fallback/`). The script will then 
	#	  create this fallback structure. If this also fails, it will exit with a fatal error to the console (F20).
	
#	0.2. If `$working_directory` EXISTS, it will check if it is writable.
	#	- If it IS writable, it proceeds normally, creating any missing subdirectories.
	#	- If it is NOT writable, it will enter a "hybrid fallback mode":
	#		- It checks if the independent `$config_file` exists and is readable.
	#			a) If YES, it will use this config file but redirect all other derived 
	#			   paths to the temporary fallback directory.
	#			b) If NO, this is a fatal error. The script will attempt to log the error to the
	#			   fallback `failure_log` and then exit (F21).
	
	# 0.3. The final derived paths (whether normal or fallback) are established and used for the remainder of the script's execution.

#	-------------------------------------------------------------------------------
#	PHASE 1. ENVIRONMENT SETUP (SELF-RE-EXECUTION) - CRITICAL STEP 

# 	1.1. The script's first action is to ensure the correct environment for the
	#	     Informix database driver. Because Perl's `use` statements are compiled before
	#	     runtime code, environment variables like `LD_LIBRARY_PATH` must be set
	#	     before the script's main logic begins. This self-re-execution is not
	#	     optional; it is the only robust method to guarantee the `DBD::Informix`
	#	     module can be loaded.
	#
# 	1.2. The script checks for a control environment variable (e.g., `$ENV{PERL_ENV_IS_CONFIGURED}`).
	
# 	1.3. **If the variable is NOT defined (first execution):**
	#	     - The script sets the control variable: `$ENV{PERL_ENV_IS_CONFIGURED} = 1;`
	#	     - It sets all required Informix environment variables (`$ENV{'INFORMIXDIR'}`, etc.).
	#	     - It constructs the `$ENV{'LD_LIBRARY_PATH'}` string, prepending the Informix library paths.
	#	     - It immediately calls `exec($^X, $0, @ARGV)` to restart itself. The new process
	#	       inherits the fully configured environment.
	
	# 1.4. **If the variable IS defined (second, re-executed run):**
	#	     - The script skips the setup block and proceeds directly to the main logic,
	#	       where `use DBI;` can now be loaded successfully.

#	-------------------------------------------------------------------------------
#   PHASE 2. COMMAND-LINE ARGUMENT PARSING

#   2.1. The script requires exactly one argument to determine its behavior. If the argument
#        count is not one, it will display help text and exit.
#
#   2.2. The script checks the argument to determine the execution mode:
#        - `-connection`: Enters Connection Test Mode.
#        - `-redo`: Enters Redo Mode.
#        - `-pause`: Enters Pause Mode.
#        - `-continue`: Enters Continue Mode.
#        - `-help`: Displays help text and exits.
#        - `<file_path>`: Enters the default Standard Processing Mode.
#        - Any other argument is invalid (log F3 and exit).

#	-------------------------------------------------------------------------------
#   PHASE 3. EXECUTION MODES

#   3.1. Connection Test Mode (`-connection`):
#        - The script attempts to connect to the Informix DB and execute the test query:
#          `SELECT CURRENT :: DATETIME YEAR TO SECOND AS date_time FROM sysmaster:sysdual`
#        - It prints a "Connection test succeeded, system current date time: <result>"
#          or "Connection test FAILED" message to the console and exits. Failure is a fatal error (F4).

#   3.2. Pause Mode (`-pause`):
#        - The script changes the content of `$mode_file` to "paused", confirms to console, and exits.
#          Failure to write is a fatal error (F5).

#   3.3. Continue Mode (`-continue`):
#        - The script first changes the content of `$mode_file` from "paused" to "online".
#        - It then processes all files found in the `$paused_dir`, triggering the full Main Workflow for each.
#        - The overall script timeout (`$max_exec_time`) applies to the entire session, but each
#          individual file within the session gets its own sub-timeout to prevent one bad
#          file from halting the entire batch.

#   3.4. Redo Mode (`-redo`):
#        - The script processes all files found in the `$unprocessed_dir`, triggering the full Main Workflow for each.

#   3.5. Standard Processing Mode (`<file_path>`):
#        - Reads `$mode_file`. If "paused", moves the incoming file to `$paused_dir`, logs the
#          action in the success log with a "PAUSED" status, and exits.
#        - If "online", proceeds to the file acquisition and main workflow.

#	-------------------------------------------------------------------------------
#   PHASE 4. NEW FILE ACQUISITION (Standard Mode Only)
	
# 	4.1. This phase only runs if the script was invoked with a file path.
	
# 	4.2. Retry Loop for File Existence:
#	     - The script will first validate the retry variables (`$seconds_between_retries`, `$max_times_to_retry`).
#	     - If both variables are not set with valid, non-zero values, the retry logic
#          is skipped, and the script will only check for the file once.
#	     - Otherwise, it will `sleep($wait_before_1st_try)` and then enter a loop, trying
#          `1 + $max_times_to_retry` times to find the `$incoming_file_path`.
#	     - On each failure, it logs a retry message to `$failure_log` (F22) and waits.
#	     - If the file is still not found after all attempts, a final failure is logged to `$failure_log` (F23) and the script exits.
	
# 	4.3. If the file is found, the script proceeds to the Main Processing Workflow (Phase 5).

#	-------------------------------------------------------------------------------
#   PHASE 5. MAIN PROCESSING WORKFLOW (MODULAR SUBROUTINES)
	
# 	This entire workflow is executed for each file. The file being processed is
# 	first moved from its source location to `$in_process_dir`. A script-wide `alarm` is
#   set using `$max_exec_time`. A timeout triggers an LME (F6).
	
# 	5.1. Data Extraction:
	# 	- Extract `$job_number` from the filename using `$job_regex_pattern`. On
	#	  failure, execute LME (F7).
	# 	- Extract `$file_format` ('ps' or 'pdf') from the filename's suffix. This
	#	  value is used for matching in the configuration file. On failure, execute LME (F8).
	
# 	5.2. Rule Lookup (Database):
	#	- Connect to the Informix database. On failure, LME (F9).
	#	- Execute `$ifx_procedure` with `$job_number`. On failure, LME (F10).
	#	- Fetch the single-column result into `$ifx_name_set`. If the result is null
	#	  or empty, LME (F11).
	#	- Disconnect from the database.
	
#	5.3. Rule Matching (Configuration File):
	#	- Parse `$config_file`. If file cannot be read, LME (F12).
	#	- Find the first line where the first column (`$name_set`) matches the
	#	  database result (`$ifx_name_set`) AND the second column (`$format`) matches
	#	  the `$file_format` extracted from the incoming filename.
	#	- If a match is found, store the third column in `$printer_dir_rule`.
	#	- If no match is found after reading the entire file, LME (F13).

#	-------------------------------------------------------------------------------
#   PHASE 6. ACTION EXECUTION

# 	6.1. Determine Action Type (Directory or Printer):
#	     - If `$printer_dir_rule` starts with a `/`, it is a directory path. Proceed to 6.2.
#	     - Otherwise, it is a printer name. Proceed to 6.3.
	
# 	6.2. Directory Move Action:
#	     - Verify the destination directory exists. If not, LME (F14).
#	     - Move the file from `$in_process_dir` to the destination directory. On failure, LME (F15).
#	     - If successful, proceed to Phase 7 with `ACTION="MOVE"` and `DESTINATION=$printer_dir_rule`.
	
# 	6.3. Print Action:
#	     - The script will execute `$printer_check_command` safely without a shell (e.g., using
#          `open()` with a pipe) to get a list of available printers. It will not
#          interpret the command string through the shell.
#	     - If the command fails, LME (F16).
#	     - If `$printer_dir_rule` is not found in the output, LME (F17).
#	     - The script will parse the `$command_for_printing` template. It will then
#          execute the command using the safe, list form of `system()` (e.g.,
#          `system('lp', '-d', $printer_dir_rule, ...)`) to prevent shell injection.
#	     - On execution failure, LME (F18).
#	     - If printing is successful, handle the processed file:
#		   - If `$save_processed_files` is enabled, move the file from
#		     `$in_process_dir` to `$processed_dir`. Log a non-fatal error on failure.
#		   - If `$save_processed_files` is disabled, delete the file from `$in_process_dir`.
#            Log a non-fatal error on failure.
#	     - Proceed to Phase 7.

#	-------------------------------------------------------------------------------
#   PHASE 7. LOGGING
	
# 	7.1. A successful operation is logged to `$success_log` in the format:
#	     `YYYY-MM-DD|HH:MM:SS|<original_filename>|<STATUS>|<ACTION>|<DESTINATION>`
#        (STATUS can be PROCESSED, PAUSED, REPROCESSED_OK, or REPROCESSED_FAIL).
# 	7.2. All errors are logged via the LME subroutine to `$failure_log` with an error code.

#	-------------------------------------------------------------------------------
#   PHASE 8. LOST AND STALE FILE CLEANUP

#   8.1. This phase runs ONLY at the end of a Standard Processing Mode (`<file_path>`) execution.
#        It does NOT run for any other command-line mode.
